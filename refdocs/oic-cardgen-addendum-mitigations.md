# OIC-PROC-CARDGEN-001 — Addendum B: Grounded Mitigations Section

**Status:** draft · **Targets:** Stage B (`resources.py`, `enrich.py`), Stage C (`render.py`)
**Depends on:** Addendum A (mitigation harvesting) · **Supersedes:** Addendum A §7 routing note
(mitigations now surface in the card, not only the source record)

## 1. Purpose

Give each card a dedicated, **grounded** mitigations section that feeds the application's later
analysis option — *identify options for reducing likelihood vs reducing impact*. Every option is
drawn from ATT&CK's own mitigation objects for the techniques **present in this flow**, never
LLM speculation. The card supplies sourced *candidates*; it does not estimate effectiveness.

This does not re-introduce control taxonomy into the cascade gates (that decision stands). It adds
a separate, discrete section.

## 2. Source

ATT&CK `mitigates` relationships: `relationship_type: "mitigates"`, `source_ref` = `course-of-action`
(an M-code mitigation), `target_ref` = `attack-pattern`. Harvest only for techniques that appear as
steps in *this* flow, so the section is scenario-specific rather than a generic catalog.

Special case: some techniques map to ATT&CK's "this cannot be mitigated with preventive controls"
course-of-action. Do **not** list it as a mitigation; instead record the step as
`no_preventive_mitigation: true` (see §7) — that is itself signal for the analysis.

## 3. Harvest (extends Addendum A §4.1)

For each mitigation attach: `id` (M-code), `name`, `description`, and the set of technique IDs in
this flow it mitigates. Resolve `course-of-action` names/descriptions once via the relationship index
already added in Addendum A; just retain the M-code and per-technique linkage rather than discarding them.

## 4. Aggregate & classify (the core)

In `enrich.py`, after steps are enriched, build a deduplicated mitigation list:

1. **Dedupe** across all steps → one entry per unique M-code.
2. Per mitigation record: `covered_steps` (step orders), `techniques` (ids), `coverage_count`
   (= number of distinct gates it touches), and `levers_touched` (the set of levers of those steps).
3. **Effect class from levers** — map to the app's two buckets:
   - `likelihood` ← lever in {`odds`, `dwell`}  (lowers the chance the chain reaches/completes a loss event → reduces LEF)
   - `impact`     ← lever in {`spread`, `size`}  (limits blast radius or loss size given the event → reduces LM)
   - `both`       ← the mitigation touches steps from each bucket
   Rationale: `spread` is treated as a magnitude lever here (containing lateral movement reduces the
   number of assets affected = loss magnitude), even though the cascade's "odds vs size" narrative
   groups it loosely with odds. This is the intended FAIR mapping for remediation analysis.
4. `coverage_count` is a **prioritization hint**: a mitigation that breaks the chain at many gates is
   higher-leverage than one touching a single step — surface it, do not collapse it.

## 5. Output

### 5.1 Frontmatter block (canonical, machine-readable — the app consumes this)
```yaml
mitigations:
  - id: M1053
    name: Data Backups
    effect: impact            # likelihood | impact | both
    covered_steps: [33]
    coverage_count: 1
    techniques: [T1486]
  - id: M1017
    name: User Training
    effect: likelihood
    covered_steps: [1, 2]
    coverage_count: 2
    techniques: [T1566.001, T1566.002]
no_preventive_mitigation_steps: [12]   # steps ATT&CK marks as not preventable
```

### 5.2 Body section (human/LLM-facing, derived from the block)
```markdown
### Reducing this risk

_Grounded in ATT&CK mitigations for the techniques in this scenario. Candidate options, not
effectiveness estimates — the quantification layer scores how much each helps._

**Reduce likelihood** (lower the chance the attack reaches a loss event)
- **User Training (M1017)** — covers steps 1–2 (the phishing entry).
- ... (one per likelihood/both mitigation, ordered by coverage_count desc)

**Reduce impact** (limit how large the loss is if it happens)
- **Data Backups (M1053)** — covers step 33 (the magnitude driver).
- **Network Segmentation (M1030)** — covers the lateral-movement steps; contains blast radius.

_Steps with no preventive mitigation in ATT&CK (e.g. step 12): rely on detection and response._
```

## 6. Provenance & no-speculation

Each option carries its M-code and the technique IDs it maps to in this scenario, so the app can
show *why* an option appears ("grounded in ATT&CK M1053 → T1486 in this flow"), not an LLM opinion.
The `mitigations:` block is **generated by code and frozen**. The LLM (Stage C) may rephrase a
mitigation `description` into plain language for the body, but must not add, remove, reclassify, or
reorder mitigations, and must not introduce any mitigation absent from the block.

## 7. Limitation (state it, don't paper over it)

ATT&CK mitigations are generic, technique-level, and skew preventive — so most land in `likelihood`,
and genuine `impact` options cluster on the `spread`/`size` steps (backups, segmentation, data
minimization). They are *sourced candidates*, not tailored controls and not effectiveness-weighted;
environment fit and quantified reduction belong to the control-maturity layer downstream. Steps
flagged `no_preventive_mitigation` are a deliberate signal that detection/response — not prevention —
is where that link is addressed.

## 8. Worked example (anchors the mapping)

- Phishing entry (T1566.x, `odds`) → **M1017 User Training**, **M1031 Network Intrusion Prevention** → `likelihood`.
- Lateral movement (T1021.x, `spread`) → **M1030 Network Segmentation** → `impact` (blast radius).
- Data encrypted for impact (T1486, `size`) → **M1053 Data Backups** → `impact`.
A mitigation touching both a phishing step and a lateral-movement step → `both`, listed under each bucket.
